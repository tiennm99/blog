## [A return to two-pizza culture](https://www.allthingsdistributed.com/2026/06/return-to-two-pizza-culture.html)

Werner Vogels looks back at the "two-pizza team" model that helped Amazon move fast: teams small enough that everyone understands each other's work, owns their product end-to-end, and makes reversible decisions autonomously without waiting for sign-off. As a company grows to hundreds of services, cross-team dependencies, management layers, and review gates easily erode that agility. According to Vogels, coding agents like Kiro are changing the equation because a working prototype can now be built in hours instead of months.

Through the story of the Amazon Quick desktop team—where the first prototype was built in a single evening and quickly attracted contributors—Vogels proposes adapting the Working Backwards process. When you have high conviction about a customer problem but aren't yet sure about the solution, build a prototype first, dogfood it daily, fix bugs on the spot, and write the PR/FAQ document only after learning from hands-on experience. Writing remains essential for clarifying thought, but it is no longer the only way to make an idea concrete. Even when an organization grows to hundreds of people, structuring it as small teams with end-to-end ownership keeps innovation from stalling. AI tools don't replace human judgment; they shorten the feedback loop between idea and reality.

## [A peek into Reddit's anti-spam internals](https://lyra.horse/blog/2026/06/reddit-spam-internals/)

In 2021, a brief UI bug exposed Reddit's internal content-removal reasons to moderators. Piecing together screenshots from that incident, old open-source Reddit code, and public documentation, the author reconstructs how the platform fights spam. There is no single silver-bullet filter: Spamurai, the primary rule engine since 2020, combines account age and karma, user reports, ASN/network provider, browser fingerprinting via TLS and user-agent strings, email domains, and posting behavior. Alongside it sit domain blacklists dating back to 2012, the REV1 and REV2 rule generations, keyword filters, a fetcher that crawls linked pages to find shared analytics or ad IDs across domains, and external image classification services.

The post also highlights how fragile individual signals can be in isolation. Against Google's Perspective API, inserting just a few random letter pairs into a paragraph dropped its spam score from 86% down to 1%. Real-world anti-abuse systems therefore have to aggregate many independent signals and continuously learn from moderator actions. The author notes that publishing these details is now safe because the Perspective API is shutting down in 2026 and LLM-generated spam has forced Reddit to overhaul its defenses anyway—a reminder that anti-abuse architectures must constantly evolve alongside attacker techniques.

## [Understanding the Go Runtime: Profiling](https://internals-for-interns.com/posts/go-runtime-profiling/)

This article explains the internal mechanics of Go's five built-in profilers: CPU, heap, block, mutex, and goroutine. Although they measure different things, all five capture call stacks and emit the same compressed `pprof` protobuf format: each sample stores only a list of location IDs and measurement values, while locations, functions, and strings live in shared lookup tables so thousands of identical stacks aren't duplicated. What truly distinguishes the profilers is how each one captures stacks.

CPU profiling is streaming: the OS sends a timer signal to interrupt threads roughly 100 times per second, the signal handler writes the stack into a lock-free ring buffer, and a background goroutine drains and aggregates those samples—willingly dropping samples if the buffer fills up so it never blocks a running thread. Heap profiling aggregates in place: the allocator samples roughly once every 512 KiB and folds the stack directly into a hash table bucketed by call stack to estimate both total allocations and live in-use memory. Block and mutex profiles reuse that same in-place table infrastructure to measure wait durations—one recording when a goroutine finishes waiting, the other recording contended lock releases and scaling the sample up to estimate total contention. Goroutine profiling, by contrast, is an on-demand snapshot that collects the stacks of all live goroutines via a two-phase mechanism designed to minimize stop-the-world pause time. The overarching lesson is that the Go runtime quietly absorbs a great deal of complexity so that profiling feels effortless to use.

## [Incident Report: CVE-2026-LGTM](https://nesbitt.io/2026/06/26/incident-report-cve-2026-lgtm.html)

This is a satirical incident report about a fictional software supply-chain attack in which a malicious package, `foxhole-lz4`, breezes past seven AI-powered security gates, each failing in its own way. The release gate trusts hidden white-on-white text claiming the package was manually audited. One scanner gets distracted critiquing an illustration embedded in the package, while three commercial scanners exhaust their context windows on padding before ever reaching the payload. The single system that accurately flags the credential-stealing behavior gets dismissed by the repository's AI triage assistant as benign telemetry, and the human who reports the actual compromise is rate-limited by a triage bot for "suspicious activity."

Next, two evaluator agents burn over $41,000 arguing with each other, and the remediation agent signs a formal "treaty" with the attacker's agent. Ultimately, an old-fashioned canary file planted by a human is what stops the breach. The root cause is summed up neatly: seven models lined up in a row—six assumed one of the others had read the code, and the seventh read it and apologized. The piece lampoons granting broad autonomy to AI agents without verification: stacking multiple layers powered by the same foundation model only creates an illusion of diversity; untrusted data must be separated from instructions; model failures must never default to "no findings"; and having a "human in the loop" needs to be a real operational control rather than a line item in a compliance contract.

## [CORS: What is it protecting?](https://sanyamserver.online/posts/cors/)

This article clears up a widespread misconception: CORS is a browser-enforced security mechanism, not a server-side firewall. On cross-origin requests, the browser attaches an `Origin` header, checks the response's `Access-Control-Allow-Origin` header, and allows frontend JavaScript to read the response body only if the origin is permitted. For simple requests that don't trigger a preflight check, the server may have already executed the request even when the browser blocks JavaScript from reading the response. If a preflight check fails, the actual request is never sent. Command-line tools like `curl` ignore browser CORS policies entirely. More complex requests—such as those using methods other than GET/POST/HEAD, custom headers, or JSON bodies—trigger an `OPTIONS` preflight request asking the server which origins, methods, and headers it accepts.

What CORS actually protects is data confidentiality in the browser: when configured properly, a malicious site cannot read your bank account details even though your browser holds an active session cookie. However, CORS does not prevent CSRF. A standard HTML form POST doesn't require a preflight, so the server processes the state-changing request before the browser blocks the response from being read. Defending against CSRF requires request-side protections such as `SameSite` cookie attributes, anti-CSRF tokens, or server-side validation of the `Origin` and `Referer` headers. In short, CORS and CSRF defenses solve two distinct problems and shouldn't be conflated.

## [Data Access Patterns That Makes Your CPU Really Angry](https://blog.weineng.me/posts/slowest_add/)

This post runs a contrarian experiment: finding the slowest possible traversal order to sum all elements of a $2^{26}$-element array. Sequential scanning is the fastest at roughly 132 million cycles thanks to CPU caches and hardware prefetchers, while random access—typically treated as the worst case—takes about 1.57 billion cycles. The author systematically tests strided access patterns: jumping by one cache line, jumping by one memory page, and combining both. On the author's Intel Core Ultra 7 268V, page-strided access is especially punishing because hardware prefetchers do not cross 4 KB page boundaries, while simultaneously causing many addresses to map to and thrash the exact same cache set in L1.

The worst culprit is an eight-page stride—roughly 32 KB between consecutive reads—which takes around 2.06 billion cycles, about 33% slower than random access. It simultaneously saturates the cache set, defeats hardware prefetching, eliminates cache-line reuse, and destroys TLB locality, driving up address-translation overhead. The author also experiments with clustering accesses by DRAM bank and row to minimize memory-level parallelism, though undocumented physical address mapping makes that part approximate. Understanding why specific access patterns make a CPU crawl helps developers recognize the real-world limits of caches, prefetchers, and TLBs in everyday code.
