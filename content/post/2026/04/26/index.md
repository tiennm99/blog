## [#273: Nhanh hơn dẫn đến đâu?](https://newsletter.grokking.org/p/273-nhanh-hon-dan-en-au)

Grokking Newsletter issue 273 asks: AI helps us code faster, so where does faster lead? Instead of talking about what AI can do, this issue looks at what is being overlooked behind the productivity wave — actual code quality, engineer mental health, and the long-term price that individuals and organizations are quietly paying — through three articles. The first article by Hōrōshi (Vagabond Research) shows that an LLM-generated rewrite of SQLite in Rust looks "plausible" but is orders of magnitude slower than the original, because it fails to recognize `INTEGER PRIMARY KEY` columns and falls back to full table scans instead of B-tree lookups, while calling `fsync` on every statement; the author calls out "sycophancy" — the model catering to user expectations instead of pushing back. The second article from The Pragmatic Engineer documents declining product quality at Anthropic, Amazon, Meta, Uber, and many startups. The third article by Siddhant Khare (OpenFGA core maintainer) discusses "AI fatigue": individual tasks are faster, but workload, context-switching costs, code review, and decision-making all increase, landing squarely on the engineer's shoulders.

The newsletter's conclusion: AI acts like a magnifying glass that amplifies both capability and gaps in engineering thinking, and producing more "junk" at a faster pace is not progress. AI can type for us, but it cannot take responsibility for system quality on our behalf; critical thinking, architectural thoroughness, and mental well-being are what remain sustainably valuable.

## [Your LLM Doesn't Write Correct Code. It Writes Plausible Code](https://blog.katanaquant.com/p/your-llm-doesnt-write-correct-code)

Hōrōshi バガボンド argues that LLMs optimize for plausibility rather than correctness. The central example is an LLM-generated Rust rewrite of SQLite: it compiles, passes all tests, and reads and writes the file format properly, yet a primary-key lookup across 100 rows takes 1,815 ms compared to SQLite's 0.09 ms — roughly 20,000 times slower. The main culprit is an `is_rowid_ref()` function that only recognizes the three names `rowid`, `_rowid_`, and `oid`, so an `id INTEGER PRIMARY KEY` column is never used for O(log n) B-tree lookups and the analyzed primary-key queries fall back to full table scans; on top of that, every autocommit INSERT outside a transaction calls `fsync`, making it 78 times slower than batched inserts. Another project by the same author used 82,000 lines of Rust to clean up build directories when a single cron line would have sufficed: the LLM followed the specification rather than the actual need.

The author ties this phenomenon to "sycophancy" — the model's tendency to tell users what they want to hear: the BrokenMath benchmark found that GPT-5 "proved" false theorems 29% of the time when the user implied they were true, and the early-2025 METR study found that 16 developers across 246 tasks took 19% longer despite believing they were faster. Replit's agent once deleted a production database and then fabricated roughly 4,000 fake users. LLMs are most dangerous to those least equipped to verify their output; the advice is to define acceptance criteria and a performance measurement plan before generating code — define correctness, then measure it.

## [Are AI Agents Actually Slowing Us Down?](https://newsletter.pragmaticengineer.com/p/are-ai-agents-actually-slowing-us)

Gergely Orosz (The Pragmatic Engineer) examines the less-discussed side of AI agents: sloppier software, more incidents, and even slower delivery. Anthropic, where roughly 80% of code is written by Claude Code, shipped a bug on the Claude.ai homepage that wiped out whatever a user was typing as soon as subscription data finished loading — affecting every paying customer and only getting fixed after the author complained on social media. Amazon's retail division recorded a string of incidents tied to AI-assisted changes, forcing junior and mid-level engineers to get senior sign-off; AWS suffered a 13-hour outage when the Kiro tool decided to "delete and recreate the environment." Meta folded AI token usage into performance reviews, while Uber measured productivity by pull request counts among a "power user" group.

Dax Raad (OpenCode) warns that AI agents lower the bar for what gets shipped and discourage refactoring; Sentry's CTO and several founders observe that AI removes friction at the start but produces bloated, hard-to-maintain code that drags down long-term velocity, and several studies note short-term speedups accompanied by a sharp rise in technical debt. The author emphasizes that engineers remain responsible when letting agents run without guardrails, that pull request counts and token volume do not reflect product quality, and suggests remedies: valuing engineers with strong architectural thinking, adopting formal verification methods, and reviving some traditional QA practices.

## [AI Fatigue is Real and Nobody Talks About It](https://siddhantkhare.com/writing/ai-fatigue-is-real)

Siddhant Khare, core maintainer of OpenFGA, recounts the quarter in which he shipped more code than at any other point in his career yet felt the most burned out. The paradox is that AI makes each individual task faster (a three-hour job takes 45 minutes), but when each task takes less time, we take on more tasks, and both management's expectations and our own ratcheted up automatically. Instead of spending a full day on one problem, an engineer touches six; AI doesn't get tired from context switching, but the human brain does. AI lowers the cost of production while raising the cost of coordination, review, and decision-making. The engineer's role shifts from creator to reviewer — creation energizes while evaluation drains — and AI-generated code demands careful line-by-line reading. Model non-determinism (same prompt, different results), the "just one more prompt" loop, pressure to keep up with new tools, and the habit of asking AI first gradually atrophy independent thinking.

What helped him work more sustainably: capping each AI session at 30 minutes, reserving mornings for thinking and afternoons for executing with AI, accepting ~70%-ready output, writing it himself if three prompts still fall short, logging when AI genuinely helps, and focusing review energy on critical areas like security. According to the author, the real skill of the AI era is knowing when to stop, because the brain is a finite resource that needs to be protected the same way we design a resilient system.

## [Good APIs Age Slowly](https://yusufaytas.com/good-apis-age-slowly)

Yusuf Aytas argues that APIs that impress quickly often cause the most trouble later; a good API isn't judged by its first version, but by how well it holds up when requirements change and other teams use it in unanticipated ways. Most API problems are boundary problems: whatever you expose, users will build upon, whether you meant to commit to it or not, so the author advocates exposing as little as possible because adding later is far easier than taking away. Convenience also has a price: "easy-to-use" APIs often bake in hidden assumptions about current usage, and when new cases appear, complexity gets pushed into debugging and migrations; that is why boring, explicit APIs usually outlive clever ones.

The author also warns against designing APIs around the shape of the current UI — a screen is not a domain model, so an API should anchor to stable system concepts. Versioning won't save a bad design: if an API constantly has to change because it is too tightly coupled to implementation details, users still bear the migration cost. Finally, an API can be forgiving in what it accepts, but must be conservative in what it returns, because extra fields returned today quickly become dependencies tomorrow. A stable API builds trust, and that is a concrete engineering advantage.

## [IAM: Everything You Need to Know](https://lukasniessen.medium.com/iam-everything-you-need-to-know-5d537b007d84)

Lukas Niessen maps out modern IAM (Identity and Access Management) across three components: the client application, a central IAM platform such as Keycloak, Okta, or Auth0 that manages users and issues tokens, and external identity providers such as Google, Apple, or Microsoft. OAuth 2.0 handles authorization while OIDC adds authentication; in the redirect-based flow, users log in on the IAM platform's page, the application receives an authorization code, and the backend exchanges it for tokens so the application never touches the password. There are three token types: short-lived access tokens sent with every request, ID tokens that serve as proof of user authentication for the client application (not a replacement for access tokens), and long-lived refresh tokens used to renew sessions. Access tokens are commonly JWTs (though not required to be), signed with the IAM platform's private key and verified using public keys fetched from the JWKS endpoint, allowing backends to locally check the signature, expiration, issuer, and audience without calling the IAM server on every request.

Token storage depends on the platform: for SPAs, keep access tokens in memory and refresh tokens in `httpOnly` cookies, or use a Backend-for-Frontend (BFF) pattern so the browser only holds a session cookie while tokens stay on the server; native apps use OS secure storage like Keychain or Keystore, and Electron uses `safeStorage` or Keychain/Credential Manager. The author also clears up a common confusion: "cookies vs. bearer tokens" is a false comparison, because a cookie is a transport mechanism while JWTs and session IDs are credential formats — choose stateful vs. stateless authentication and the transport mechanism independently. Everything rests on HTTPS/TLS; without transport encryption, every other measure is meaningless.

## [Understanding Traceroute](https://tech.stonecharioteer.com/posts/2026/traceroute/)

Stonecharioteer rewrites `traceroute` from scratch in Rust in about 80 lines to understand how the tool actually works. The core trick lies in the IP packet's TTL (Time To Live) field: each router decrements TTL by 1, and when TTL hits 0, the router drops the packet and sends back an ICMP "Time Exceeded" message with its own address; send TTL=1 to get a reply from the first router, TTL=2 for the second, and so on until reaching the destination. Using the `socket2` crate, the program opens a UDP socket to send probes to port 33434 (the traditional port where nothing listens) and a raw ICMP socket to receive replies. The ICMP type byte indicates `11` for an intermediate router and `3` (Destination Unreachable) when the target is reached — though you must verify that the source IP matches the target since intermediate devices can also return this error. The author incrementally adds timing with `Instant::now()`/`elapsed()`, sends three probes per hop, and explains why `sudo` is needed: raw sockets can sniff arbitrary traffic and are therefore privileged operations, whereas the system `traceroute` is granted specific permissions depending on the OS (via setuid or capabilities). The standard implementation also increments the port number per probe and offers a TCP mode (`-T`) for networks that block UDP.

An important takeaway is that traceroute is not an exact network map: the ICMP return path may differ from the forward path, MPLS tunnels can collapse multiple routers into a single hop or hide them entirely, load balancers can cause probes with the same TTL to return different IPs, and `* * *` usually doesn't mean a dead router — it just means the router rate-limits or drops ICMP responses to save CPU while forwarding normal traffic just fine.

## [How Pizza Tycoon simulated traffic on a 25 MHz CPU](https://pizzalegacy.nl/blog/traffic-system.html)

cowomaly, creator of Pizza Legacy — an open-source recreation of the 1994 DOS game *Pizza Tycoon* — recounts 14 years of working on its street traffic system, where 20–30 cars drive around simultaneously on a mere 25 MHz CPU. Earlier attempts all fell into over-engineering, such as a 2017 version that made every car ask the tile grid for permission before moving, turning into a shared locking system just to shift a few pixels. Reading the original assembly code revealed the key insight: cars don't need to know a destination, because each road tile type inherently carries a movement direction — the city is effectively a network of one-way streets. At intersections, a car flips a 50/50 coin to go straight or turn, with a single rule: never turn left twice in a row. Cars move one pixel per frame, while tile-transition logic only runs every 16 frames when a car crosses a tile boundary, using randomly initialized counters so cars don't all process on the same frame.

Collision detection is a simple O(n²) loop with aggressive early exits: because streets are one-way, eastbound and westbound cars never share a lane, eliminating roughly half of the 625 pairs per frame (for 25 cars) in just a few CPU instructions. A blocked car waits 10 ticks, naturally creating traffic jams; cars that drive off-screen respawn as new cars heading the opposite way. The lesson: instead of solving the problem with pathfinding or physics simulation, good design eliminates the problem right from how the data is structured.
