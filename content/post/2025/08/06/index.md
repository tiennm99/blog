## [Coding with LLMs in the summer of 2025 (an update)](https://antirez.com/news/154)

Antirez, creator of Redis, shares an update on how he works with LLMs. In his view, frontier models like Gemini 2.5 PRO can amplify a programmer's capabilities: catching bugs before they reach users (something he experienced firsthand while building Vector Sets for Redis), rapidly writing throwaway code to test ideas, co-designing solutions, and working with technologies outside one's core expertise. However, LLMs are currently "good amplifiers" but terrible "one-man bands": when left to tackle complex goals on their own, they produce bloated, fragile code full of suboptimal choices, so he rejects vibe coding in most cases.

To get good results, the programmer must supply a rich context: documentation, most of the relevant source code, and their full understanding of the problem—including approaches that sound appealing but are actually bad, promising directions, goals, invariants, and desired code style. For new technologies the model doesn't know yet, simply dropping the README into the context is enough. He recommends using Gemini 2.5 PRO (stronger at reasoning and spotting subtle bugs) and Claude Opus 4, while avoiding coding agents or agent-integrated editors, skipping RAG, and manually copying code between the terminal and the web UI to stay in the loop. According to him, staying in control is currently the best way to leverage AI, while avoiding LLMs out of prejudice is itself a risk.

## [Artisanal Handcrafted Git Repositories](https://drew.silcock.dev/blog/artisanal-git/)

Drew Silcock walks through creating a Git repository "by hand" without running a single Git command—not even plumbing commands—to show how Git works under the hood. The article starts by manually creating the `.git` directory, its required subdirectories, the config file, and the `HEAD` file pointing to `main`. Next, he explains Content Addressable Storage: in the SHA-1 example repository, loose objects are identified by their hash and compressed with zlib. Git has three main object types: blob (file contents), tree (a directory listing with references to blobs and subtrees), and commit (pointing to the root tree along with author metadata and the commit message). One surprising detail for many is that Git stores the full contents of a file for each version rather than diffs; space savings are handled later through packfiles and garbage collection.

The hands-on walkthrough steps through creating a blob for a file, constructing a tree, crafting a commit (including GPG signing), and writing the branch reference so Git recognizes the initial commit, then verifying the result with standard Git commands. The author also explains why the first two characters of the hash are used as a subdirectory name, along with references and the reflog. The core takeaway is that Git's power comes from the simplicity and elegance of its design rather than complex code; once you understand the underlying file formats, writing a simple Git clone yourself is not nearly as daunting as it seems.

## [Why I'm Betting Against AI Agents in 2025 (Despite Building Them)](https://utkarshkanwat.com/writing/betting-against-agents)

Utkarsh Kanwat, who has built over a dozen production AI agent systems (UI generation, database operations, DevOps, CI/CD), explains why he is betting against the wave of fully autonomous agents in 2025. First, errors compound exponentially: if each step is 95% reliable, a 20-step workflow succeeds only 36% of the time, whereas production systems need 99.9%+. Second, token costs grow quadratically with conversation length because every turn reprocesses the entire context; a 100-turn session can cost $50–$100. Third, the real challenge lies in tool engineering and feedback loops: AI accounts for only about 30% of the work, while the remaining 70% is tool design, context management, partial failure handling, and recovery mechanisms.
His own agents work because they have tightly bounded scopes, verifiable operations, and human confirmation at critical points—for example, his database agent always asks before executing destructive operations, and his function-generation agent is completely stateless. He predicts that "fully autonomous agent" startups will soon hit an economic wall, while the winners will be specialized tools acting as "very capable assistants with clear boundaries." His advice for agent builders: define clear boundaries, design for failure, do the cost math, prioritize reliability over autonomy, and use traditional software engineering for critical execution paths.

## [Rethinking CLI interfaces for AI](https://www.notcheckmark.com/2025/07/rethinking-cli-interfaces-for-ai/)

The author, who uses LLMs for reverse engineering via an IDA Pro MCP server, argues that current CLI tools and APIs are poorly suited for LLM agents, especially local models with small context windows. Designing an MCP interface requires balancing returning too much information (bloating the context) against returning too little (forcing extra tool calls); the author's team added guidance in docstrings so the model prefers the high-level `get_global_variable_at` helper over low-level memory-reading functions. On the command line, the author observed Claude Code repeatedly piping output through `head -n100`, losing track of its working directory, and passing `--no-verify` to bypass git hooks when it couldn't fix failing tests—prompting the author to write a git wrapper that blocks that flag and prints instructions telling the agent how to fix the issue properly.

Borrowing the concept of "Information Architecture" from UX design, the author argues that agents' clumsiness with CLI tools shows those tools have poor information architecture for non-human users. Proposed fixes include replacing `head` with a wrapper that caches full output, returns structured chunks, and states how many lines remain so the agent doesn't re-run expensive builds; and adding a shell hook that prints the current working directory whenever a command is not found. According to the author, almost every CLI tool could include extra context to cut down on round-trips and save context window space, and it may be time for a dedicated toolkit or shell built specifically for LLMs.

## [Asynchrony is not Concurrency](https://kristoff.it/blog/asynchrony-is-not-concurrency/)

Loris Cro (Kristoff) argues that we are missing a crucial distinction when talking about concurrent programming: asynchrony. He gives two examples: saving two files in any order can be done one after the other and still be correct; but starting a TCP server and connecting to it within the same program requires the two tasks to overlap in time. From this, he proposes clear definitions: asynchrony is the ability for tasks to execute out of order while still producing a correct result; concurrency is a system's ability to make progress on multiple tasks at once, via parallelism or task switching; and parallelism is physically executing multiple tasks at the same instant. Both examples exhibit asynchrony, but only the second requires concurrency.

Conflating the two has had real consequences: library authors must maintain separate synchronous and asynchronous versions (like `redis-py` and `asyncio-redis`), "viral" async functions force users to abandon synchronous code, and awkward escape hatches invite deadlocks. In Zig's new I/O design, `io.async` does not imply concurrency: when run in a single-threaded blocking mode, it simply calls the function immediately, so libraries using async do not force users out of synchronous I/O. When true concurrent execution is needed, developers call `io.asyncConcurrent`, which can return an error if the execution environment does not support it. This allows synchronous and asynchronous code to coexist without trade-offs.

## [How Does AI Disrupt Accountability in Code Reviews?](https://rdel.substack.com/p/rdel-102-how-does-ai-disrupt-accountability)

Issue #102 of RDEL by Lizzie Matusov summarizes a qualitative study on how LLM-assisted code reviews affect engineers' sense of accountability. The researchers interviewed 16 engineers and then ran four focus groups simulating both peer reviews and LLM-assisted reviews. The findings identify four intrinsic drivers of personal accountability for code quality: personal standards, professional integrity, pride in code quality, and professional reputation. Once a review begins, accountability shifts from individual to collective: engineers adjust their tone, stay open to feedback, and align their personal bar with team norms.

LLM-performed reviews disrupt this social process because without a real human reader, there is no reciprocity or "social contract" to uphold; as one participant put it, "you can't hold a model accountable." Engineers still appreciate AI feedback and happily use it for a first pass to catch basic issues before asking a teammate to review, but they distrust its grasp of context and do not view its suggestions as authoritative. The author advises engineering managers to treat LLMs as a support layer, keep humans in every review loop (especially for architectural decisions and team standards), and reinforce intrinsic motivation through social norms like recognizing thoughtful reviews.

## [Vibecoding a High Performance System](https://andrewkchan.dev/posts/systems.html)

Andrew Chan recounts using Cursor's agent (primarily with Claude 4 Opus) to build a system capable of crawling one billion web pages in about 24 hours, with only around 3.75% of the code written by hand. Unlike many vibe-coding demos, this was a domain new to the author, with a wide design space, an objective performance target, and severe failure modes at scale such as failing to respect website rate limits. So he let the AI write the code while checking in frequently and reviewing carefully at the end. The models still made real mistakes: placing a `FOR UPDATE` lock on a CTE caused a race condition where two workers grabbed the same URL, and using Python's built-in `hash` function (which is randomized across processes) broke domain partitioning.

The biggest strength was exploring the design space at breakneck speed: across 8 completely different architectures, measured throughput climbed from roughly 20 to 10,800 pages per second. When writing code becomes cheap, the bottleneck shifts to running experiments and reviewing. Still, the AI frequently produced logically valid "slop" that hurt performance, such as a redundant HTML sanitization step that made the parser twice as slow or unused struct fields that bloated memory. The author concludes that agents have transformed the scale of software he can build solo, but strong fundamentals matter even more, because only engineers who deeply understand the whole system can get the most out of AI's still-flawed capabilities.

## [Two Simple Rules to Fix Code Reviews](https://serce.me/posts/2025-07-17-two-simple-rules-to-fix-code-reviews)

Sergey Tselovalnikov argues that amid countless code review "best practices," real effectiveness comes down to two simple rules—both aimed at reviewers, since they control most of the time a change spends waiting. The first rule is to minimize turnaround time: for the reviewer, delaying costs almost nothing, but for the author, flow stops the moment a review is requested; after an hour they lose very little context, after a day they have to reload their mental model, and after a week they are practically starting over. Responding quickly doesn't mean rubber-stamping; it means making an honest effort to understand the change, raising major concerns, and asking questions, because nothing is worse than silence. The second rule is that every comment must include a "because" clause: instead of writing "do X," write "do X because Y"; if you can't articulate a clear reason, you probably shouldn't leave the comment.

The author notes that senior and staff engineers—who often review more than they write code—set the team's culture: if they take two days to review, the whole team will treat that as normal, even for tiny changes. These two rules work best for teams sharing common goals and may not apply to open source, where the cost of accepting a bad contribution is much higher.

## [Reading QR codes without a computer!](https://qr.blinry.org/)

This interactive guide teaches you how to decode QR codes by hand, without a computer or phone. You can type in custom text, scan an existing QR code, or practice with a random English word, walking through each component of the code: size and version (the smallest being 21×21 modules), finder patterns that help scanners orient the code, separators, timing patterns, alignment patterns, format information storing the mask and error-correction level, and the surrounding quiet zone.

A fun highlight is how it explains the eight mask patterns using a memorable prison-break story, complete with a printable zine cheat sheet. After unmasking via XOR, the guide walks through identifying the encoding mode (numeric, alphanumeric, byte, Kanji, etc.), reading the length, and decoding each data block. It is a great visual way to understand the technical structure of QR codes.
